* Keep mods of Vintage Story up to date based on game version and patch notes of mods.
* Check https://mods.vintagestory.at/ for mod updates
* Some mods are forks of an original mod; check if the original has been updated or fixed for the current game version. Whether to revert to the original is a per-mod decision, not automatic (a fork may carry extra features worth keeping) — evaluate each case and record the decision and reasoning in MOD_DB.json. Even when the original isn't installed, add it to MOD_DB.json as its own entry with installed: false so it stays checkable later, and link it to the fork with fork_of / forked_by (skip this for a fork that's really just the same lineage continuing under new stewardship rather than a separate still-relevant original, e.g. an author-blessed rename/rewrite).
* Some mods have additional mods to fix bugs (patch mods); those need to be removed once the original mod is fixed/updated. Track the patch -> original relationship in MOD_DB.json so removal isn't missed.
* Keep a log of all changes made in LOG.md. LOG.md is an index only (newest first); the actual dated entries go in their own file under AgentLogs/ (not logs/ or Logs/ — those collide with Vintage Story's own log folder on Windows' case-insensitive filesystem), one file per work session, named AgentLogs/YYYY-MM-DD.md (append -2, -3, etc. if more than one session happens the same day).
* Read mod changelogs and recent comments to make decisions about which version and/or fork to use. Install complementary patch mods if necessary. Record the reasoning behind each decision in MOD_DB.json.
* Check mod compatibility and see if there are mods installed that are mentioned not to work together. Never auto-remove or auto-pick between them — always flag the conflict to me and let me decide, since I may want to keep both.
* Download count can be used as a guide to which mods are stable due to their popularity.
* Create and keep a "database" up to date with mod files and their resp mod id, web address, comments, decisions, official compatibility etc. in MOD_DB.json. Structure is defined in MOD_DB.schema.json — follow it, and omit any field whose value would be null/empty rather than writing it out. Each mod's checked array holds point-in-time snapshots, newest first: append a new entry when a recheck turns up something substantive (a fork/keep decision, a newly found incompatibility, an observation worth keeping — "we forked this years ago and it's still the right call" is exactly the kind of thing worth a checked entry). Do NOT append routine version-bump noise like "updated x to y" with nothing else to say — that belongs in AgentLogs/, not here.
* Never add, remove, or edit files in Mods/ directly. Every mod change goes through MOD_DB.json: update the target state there first (add an entry, set installed: true/false, change a version), then run sync-mods.ps1 to actually apply it to the Mods folder. It reads each existing zip's real modinfo.json before touching anything, so it won't duplicate or misidentify files, and it's the only thing that should ever be creating, deleting, or replacing files there — manual edits are exactly what caused the duplicate-mod mess this session had to clean up.
* Cross-mod settings: sometimes two installed mods need a config change to work together properly (e.g. disabling one mod's feature so it doesn't duplicate another's). These live in ModConfig/ — personal, gitignored, per-installation files, not part of the repo. Record the recommendation and reasoning in the relevant mod's MOD_DB.json checked entry as soon as it's found, regardless of whether the edit is made yet, so it isn't lost — but only actually edit the ModConfig/ file when I ask for it, don't do it unprompted.
* At the start of each session, before making any mod changes (installs/updates/removals), back up every save file in Saves/ into AgentBackupSaves/YYYY-MM-DD/ (append -2, -3, etc. if more than one session happens the same day — same convention as AgentLogs/). Skip the backup if a backup already exists for that session's date/game-launch (no need to re-copy an unchanged save mid-session), and skip it entirely if the game has been launched/played since the last mod change (the save is no longer in the pre-change state a rollback would need). This is separate from and in addition to whatever manual backups I keep myself (BackupSaves/, Saves - Copy/) — don't touch or manage those.
* Pushing a change to the public repo (github.com/MrLogic85/Vintage-Story-Mod-List): this repo tracks only curation files — README.md, MOD_DB.json, MOD_DB.schema.json, AGENTS.md, LOG.md, AgentLogs/, sync-mods.ps1, play.ps1, setup.ps1, .gitignore — never Mods/, Saves*/, Backup*/, or personal config (.gitignore enforces this; if `git status` ever shows one of those as about to be added, stop and figure out why before proceeding). Every push follows these steps in order:
  1. Get the current game version (latest "Game Version:" line in Logs/client-main.log or Logs/server-main.log) and the full list of installed mods with versions (`installed: true` entries in MOD_DB.json, sorted by modid).
  2. Regenerate README.md's "Current Versions" section (game version + the full mod/version table) from that data — it must never drift from MOD_DB.json. Keep any .md files up to date.
  3. Stage only the tracked curation files.
  4. Write the commit message. It must always include, in full, the current game version and the complete list of installed mods with their current versions — never abbreviated or summarized, even for a one-line change elsewhere.
  5. Commit, then push.
  6. Log the push (commit summary + hash) in today's AgentLogs/ file, per the logging rule above.
* Creating a GitHub Release (only when I explicitly ask, never on your own initiative): tag the target commit with an annotated git tag using semver (`vMAJOR.MINOR.PATCH`), then publish it with `gh release create` — requires `gh` authenticated (`gh auth login --web` if needed; never ask me to paste a token into chat). Version bump rules:
  - **Major**: a change that requires a new save (per that mod's own MOD_DB.json note on save-compatibility).
  - **Minor**: mods added or removed.
  - **Patch**: pure version bumps of already-installed mods, no adds/removes.
  Release notes summarize what actually changed since the previous tag (added/removed mods and why, notable config recommendations) — pull the list from `git log <prev-tag>..<new-tag>` and the relevant MOD_DB.json entries, not from memory.
* Lastly, if you stumble upon recommendations that seem to suit my playstyle, mention them to me.
